## 1. ★★★ FND-066：`--fit` 与 `--n-cpu-moe` **互斥**（本会话最重要的机制发现）

`--n-cpu-moe N` 内部编译成一组 `-ot` 张量覆盖（`blk.0..N-1` 的 `ffn_*_exps = CPU`），
而 **`common_fit_params()` 只要发现 `tensor_buft_overrides` 非空就直接放弃 fit**。

**推论**：
1. MoE 条目上的 `--fit on --fit-ctx N` 是**装饰性的，从未生效**；
2. 这解释了为什么 `--fit-target` 改与不改毫无差别；
3. **「`--n-cpu-moe N` + `--fit on` 当安全网」这个设计前提不成立** ——
   **MoE 模型没有自动降级兜底，`n-cpu-moe` 设错的后果是 OOM，不是优雅降级。**

> ⚠️ **方法论**：日志里的 fit abort 提示**不是可靠判据**。
> 26B-A4B 的运行日志里**没有** abort 提示，但 fit 同样无效。
> **只有 A/B 对拍才算。**（26B @131072：带 fit 10,398 MiB / 39.7 t/s，不带 10,398 MiB / 40.3 t/s —— 显存一字不差。）

**修复面**：`make_auto()` 的 MoE 分支**只输出 `--n-cpu-moe N`**，不再输出 fit；
`strip_decorative_fit()` 清理存量；`find_moe_gaps()` 新增 `fit` 缺陷类型。

## 2. ★★ `-ub`（ubatch）陷阱：**单独提完全无效**

### 2.1 陷阱

`llama.cpp` 要求 `n_ubatch <= n_batch`，并且是**静默 clamp，不警告**。

第一版探针只改 `-ub`（`--batch-size` 钉在 512）：

| batch / ubatch | prefill t/s | VRAM |
|---|---:|---:|
| 512 / 512 | 955.6 | 11,628 |
| 512 / **2048** | 971.7 | **11,628** ← 一 MiB 不差 |

**VRAM 完全相同就是"参数被吃掉了"的铁证。**

### 2.2 正确做法：成对提升

Q5 @ ctx 65536 / n-cpu-moe 27 / ~14.7K prompt：

| batch / ubatch | prefill t/s | decode t/s | VRAM | 余量 |
|---:|---:|---:|---:|---:|
| 512 / 512 | 955.6 | 59.6 | 11,628 | 4,683 |
| 1024 / 1024 | 1,426.5（**+49%**） | 62.2 | 11,710 | 4,601 |
| **2048 / 2048** | **1,866.7（+95%）** | 62.0 | **11,872** | **4,439** |

**机制**：CPU 侧专家张量**每层每个 ubatch 搬运一次，与 ubatch 大小无关**
⇒ 每 ubatch 塞更多 token = **纯摊销**，解码不受影响。

### 2.3 顺带标定 compute buffer 斜率

两个独立差值互证：512→1024 = +82 MiB，1024→2048 = +162 MiB
⇒ **0.160 / 0.158 MiB per batch unit**（吻合 1.4%）。

⚠️ 但**只标定斜率，不编截距** —— 截距没有被干净的 A/B 分离出来。

## 3. `--no-mmap` → `--load-mode none`：不是"顺手换新写法"

社区实测（#28363）：**`--n-cpu-moe` + mmap 会掉 60% prefill**，
必须 `--load-mode none`（同一二进制 22.7K 上下文 **1,293 → 2,145 t/s**）。

⇒ 启动器里那 14 处 `--no-mmap` 不是"已废弃所以顺手换"，而是一个 **60% prefill 的性能洞**。
`--load-mode none` 的语义 = 「no special loading mode」= 关闭 mmap（已核实等价）。

## 4. GGUF 张量表解析（纯标准库）

### 4.1 必须**按长度 seek 跳过 KV 区**

`read_gguf_meta()` 只读头部 1 MiB —— 够拿到架构键，但**永远到不了张量表**：
张量表在**整个 KV 区之后**，而 tokenizer 数组单独就有数 MB。

正确做法：逐个 KV 读 key + type，**按声明长度 seek 跳过 value**，再读张量表。

### 4.2 ★ 专家张量有**两种命名形态**，而且大小校验查不出漏掉

| 模型 | 命名 |
|---|---|
| Qwen | `ffn_gate_exps` + `ffn_up_exps`（**分开**） |
| Gemma | `ffn_gate_up_exps`（**融合**） |

第一版正则只列了分开的 ⇒ **Gemma 的专家占比算成 30%（实际 90%）**。

> **为什么文件大小交叉校验查不出？** 因为它验的是**总量** —— 总量不受分类错误影响，
> **只有专家/非专家的切分错了**。
> ⇒ 解析器必须额外返回**匹配到的命名模式**并打印出来。以后出现第三种形态一眼可见。

**明确排除**（名字很像但不是 `--n-cpu-moe` 搬运的对象）：
`ffn_gate_inp`（路由器）、`ffn_*_shexp`（共享专家）。

### 4.3 ★ 专家字节按层**非均匀**

| 模型 | 层 | E/层均值 | **层间极差** |
|---|---:|---:|---:|
| `gemma-4-26B-A4B-it-qat-UD-Q4_K_XL` | 30 | 408 MiB | **0%** |
| `Gemma4-26B-A4B-...-HauhauCS` | 30 | 481 MiB | **17%** |
| `Qwen3.6-35B-A3B-UD-Q4_K_XL` | 41 | 468 MiB | **17%** |
| `Qwen3.6-35B-A3B-Uncensored-...` | 40 | 518 MiB | **31%**（末 6 层 630 MiB，比中段大 46%） |

⇒ `--n-cpu-moe N` 移除的是**前 N 层实际字节**，不是 `N × 均值`
⇒ 必须走**真实累积曲线** `cum(N) = Σ per_layer[0..N-1]`

### 4.4 ★★ 两条**独立**方法互证

| 来源 | Q5 每层专家字节 |
|---|---|
| GPU 行为反推（由实测阶梯回归） | **531 MiB** |
| GGUF 张量表直算（与 GPU 无关） | **518 MiB** |
| 差 | **2.5%** |

**⇒ VRAM 模型和解析器互相确认，两者都可信。**

## 5. 不伪造系数（工程原则）

`compute_buf_gb(batch, vram_calib)` 按 batch 缩放 compute 预算，**斜率从标定数据读**。
没有斜率时**明说「未标定」**，而不是编一个。

> 单点标定**推不出斜率**。编一个会让估计"看起来精确但其实是虚构的"，
> 而且 OOM 该来时照样来。**宁可承认不知道。**

同理：`start_ratio` 下限**只在没有张量表时**才用作兜底 ——
精确曲线说 27 时，粗糙的比例说 30，**27 才是对的**（实测验证）。

## 6. 回归方法论（本会话沉淀的四条）

### 6.1 断言上线**立刻**抓到 3 个真实缺陷

写完 E 组断言第一次运行就报出：
1. 🚨 **FND-064 复发** —— 用户手动改的 `n-cpu-moe 27` **根本没进 `.bat`**（启动器侧仍是 20）
   ⇒ 不走 Router 直接双击启动器 = **再次 OOM**。**改 override 后必须跑一次更新器。**
2. 14 处 deprecated `--no-mmap`
3. **告警自身误报**（见 §6.2）

### 6.2 ★ 告警/断言自己也会误报 —— 必须先跑一遍

`DECORATIVE_FIT_RE` 把菜单横幅 `echo --fit 自动分层, KV=q8_0` 里的**散文**当成了参数
⇒ 每次运行都报「2 个 MoE 条目缺 `--n-cpu-moe`」并建议 `--fix-moe`，
而 `--fix-moe` **永远修不动它** —— 一个**永远无法消除的告警**。

**我自己写的第一版断言也犯了同样的错。**
⇒ 三处定义统一为「只匹配带值的两种形式」：`--fit-ctx N` / `-fitc N` / `--fit on|off`。

### 6.3 ★★ 负向对照 + 变异测试：证明断言**真的有效**

- **`--self-test`**：9 个故意写坏的 body，每个断言必须**触发**才算通过。
  > 「一个对什么都通过的检查毫无价值」—— 这些 bug 之所以能发布，正因为当时没有任何测试失败。
- **变异测试**：把 `TUNE_MIN_HEADROOM_MIB` 3072 → 8192 ⇒ **FAIL (2 problems)** ⇒ 恢复 ⇒ PASS。

### 6.4 ★★ 两个真实点**可能都不约束规则**

原本用用户自己的两个 OOM 实测点做断言：n=27（4,782 MiB ✅）/ n=20（1,065 MiB ❌）。
**但 4,782 能过任何合理阈值，1,065 过不了任何阈值** ——
**两个点都没有约束住 3 GB 这条规则本身。**

⇒ 补上**跨越阈值**的两例：n=24（3,189 ✅）/ n=23（2,658 ❌）。
改 `TUNE_MIN_HEADROOM_MIB` 现在会失败，之前会**滑过去**。

### 6.5 ⚠️⚠️ `__pycache__` 假失败陷阱

把 `3072` 改成 `4096` —— **两者都是 4 字符，文件大小不变**；
而恢复文件时**保留了原 mtime**。Python 的 `.pyc` 校验**只看 mtime + 大小**
⇒ 两者都"没变" ⇒ **继续跑被污染的字节码** ⇒ 源码明明已恢复正确却仍然 FAIL，白查一轮。

**⇒ 变异测试铁律：要么改成长度不同的值（如 `8192  #`），要么先清 `__pycache__`。**

### 6.6 hub 层曾**零覆盖**

回归套件只读**生成物**（`.bat` / `ini`），完全碰不到 `llama_hub.py` —— 而它才是
用户天天操作的界面（菜单 / `--guide` / `--audit` / 参数编辑器）。
⇒ 新增纯函数断言组（16 例，全部对**真实实测数据**断言，不是为了让测试通过而编的数）。

## 7. 沟通与流程教训

### 7.1 ★ 大体积操作前必须讲清「产物与原文件的关系」

用户对"22 GB 拷贝"的合理困惑暴露了沟通缺口。**执行任何大开销/大体积操作前，用一句话说明**：
1. **产物是什么** —— 是"同一个东西 + 补丁"（merge），还是"一个新东西"（adapter）
2. **是否互相依赖** —— merge = 零依赖完整文件；adapter / LoRA / 外挂 draft = 依赖基座
3. **删掉原文件会怎样** + 产物能否独立运行

### 7.2 图索引不可用时的等价影响分析

GitNexus 未索引本仓库 ⇒ `detect_changes` / `context` / `impact` 都跑不了。
替代方案（对 2–3 个 Python 文件的规模**比图索引更直接**）：
`git status` 分类 → `grep` 真实调用关系 → 逐符号判断契约变化（签名/返回语义/迁移别名）。

### 7.3 提交卫生：重组与行为改动**必须分开**

- `git diff --stat HEAD` 会把**已 staged 的重命名**显示成"全是新增" ⇒ **审阅者看不到真实改动**
- **`R100`（100% 相似度的纯改名）让拆分成为可能**：不带 `-a` 的 `git commit` 提交的是**改动前的旧内容**
  ⇒ 第一个提交是干净可复核的重组，行为改动全在第二个提交
- `.gitignore` 要挡掉**测量产物**（`plan/_*.json`、`plan/_*.png`），但**保留探针脚本** ——
  计划文档里每个数字都是它们产出的，必须可复现
